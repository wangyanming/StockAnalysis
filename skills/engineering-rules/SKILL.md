# 工程规范（StockAnalysis）v6.0

**适用场景：** StockAnalysis 项目开发。AI 开发必须按「流程 + 规范 + 检查」三步执行，禁止自由发挥。

**强制原则（无例外）：**
- 所有代码必须遵循本规范
- 禁止私自改架构、禁止无注释代码
- 数据类代码必须做单位校验 + 合理性校验
- 所有修改必须可追溯、可验证、可回滚
- 文档与代码必须同步更新

---

## 1. 项目目录结构（目标结构）

**新模块按此结构存放，存量代码逐步迁移**，不搞一次性重构。

```
StockAnalysis/
├── main.py                  # 主入口
├── configs/                 # 配置文件（数据库、API、定时任务）
├── core/                    # 核心业务模块
│   ├── fetcher/             # 数据采集
│   ├── analyzer/            # 计算分析
│   ├── picker/              # 选股策略
│   └── reporter/            # 报告生成
├── utils/                   # 工具类（日志、HTTP、数据库、校验）
├── data/                    # 数据文件/缓存
├── tests/                   # 测试脚本 + 质量门禁
├── docs/                    # 需求/架构/测试/部署文档
│   ├── requirements/        # 需求文档（由 requirement-doc skill 生成）
│   └── design/              # 方案设计（由 design-doc skill 生成）
├── logs/                    # 运行日志
├── skills/                  # 本地技能定义
├── memory/                  # 每日记录（软链到 openclaw workspace）
├── PROJECT_STATE.md         # 项目实时状态（必读）
├── MEMORY.md                # 长期经验沉淀
└── requirements.txt         # 依赖清单
```

## 3. 开发全流程规范（10 步，必须逐行执行）

### 3.1 改前必做（不可跳过）

1. 读取 `PROJECT_STATE.md`，明确当前状态
2. **读本 skill**（没错，你正在读的就是），确认当前规范全部条款
3. 明确本次改动目标、影响文件、影响范围
4. 检查是否有同类代码需要同步修改
5. 确认数据单位、字段、接口规则
6. 确认关联需求/方案文档已存在

### 3.2 开发过程

1. 使用项目统一代码模板，不手写裸代码
2. 必须加注释：功能、参数、返回、异常、单位转换
3. 禁止 magic number（无注释硬编码）
4. 异常必须捕获，不能静默失败
5. 数据采集必须做：非空、范围、阈值、单位校验

### 3.4 AI 改前自检清单（强制）

**每次开始写代码前，必须口头过一遍以下清单，不可跳过：**

```
✅ [确认] 需求范围是否明确？影响哪些文件？验收标准是什么？
✅ [文档] docs/requirements/ 下是否有匹配的需求文档？无 → 先生成
✅ [文档] docs/design/ 下是否有方案设计？复杂改动无 → 先生成
✅ [状态] PROJECT_STATE.md 是否已读？当前项目状态是否清晰？
✅ [规范] skills/engineering-rules/SKILL.md 是否已读？最新版本？
✅ [改后] 改完后是否会跑 tests/check_engineering.sh？
```

**规则：** 检查未通过前，禁止写任何代码。

### 3.5 改后必做（不可跳过）

1. 运行质量门禁脚本：`bash tests/check_engineering.sh`
2. 运行端到端验证，确保流程不中断
3. 数据结果校验（偏差 < 5%）
4. 更新文档：`PROJECT_STATE.md` + `MEMORY.md`
5. 问题必须闭环，扫描同类问题
6. **按固定格式输出改后总结（见第 8 条）**

## 4. 代码编写规范

### 4.1 通用规则

- 变量名/函数名：见名知意，禁止 `a`/`b`/`c` 单字符
- 一个函数只做一件事，长度不超过 80 行
- 禁止深层嵌套（不超过 3 层）
- 日志等级：INFO / WARNING / ERROR 必须明确

### 4.2 数据代码强制规范（最高优先级）

- 采集代码第一行：注明数据源单位
- 单位转换必须加注释：`# 手 → 股 ×100`
- 校验公式：`amount / volume ≈ close` 偏差必须 < 5%
- 不同板块（主板/科创/北交）单位必须统一
- API 失败必须有重试机制（3 次）

### 4.3 数据库规范

- 连接必须使用统一工具类（`dao.py`）
- 禁止裸写 SQL，防止注入
- 写入前必须校验数据格式
- 操作必须带日志

### 4.4 异常与告警规范

- 异常必须输出明确信息
- 数据异常必须触发告警，不隐藏
- 定时任务必须输出执行结果
- 禁止空 `except` 捕获

---

## 5. 质量门禁规范

### 5.1 必须通过检查

- 语法检查：无报错、无警告
- 工程规范：目录、命名、注释合规
- 数据校验：单位、范围、偏差合规
- 数据库检查：连接正常、核心表存在
- 模块检查：可正常导入、无循环依赖

### 5.2 检查不通过处理规则

- AI 必须自动修复，禁止提交人工
- 修复后重新检查，直到通过
- 无法修复必须记录根因，更新文档

---

## 6. 文档规范

- 代码改动 → 文档必须同步改
- `PROJECT_STATE.md`：记录状态、问题、改动点
- `MEMORY.md`：记录坑点、经验、最佳实践
- 所有接口、字段、单位必须写进文档
- 禁止只写代码、不写文档

---

## 7. 安全与红线规范

- 禁止泄露隐私数据
- 删除文件优先使用 `trash`，禁止直接 `rm`
- 禁止线上环境直接操作
- 禁止未经确认执行破坏性命令
- 配置文件不提交 git，禁止明文密钥

---

## 8. AI 开发输出固定格式（强制）

每次改完代码后，必须按以下格式输出总结：

```
【改动文件】xxx.py, yyy.py
【改动目标】一句话说明本次改了什么
【影响范围】改了 A 会影响 B、C、D
【代码说明】关键逻辑简述
【数据校验结果】字段名=原始单位→目标单位, 偏差X%（<5%✅）
【检查脚本结果】✅ check_engineering.sh 全部通过
【验证步骤】1. xxx 2. yyy 3. zzz
【更新文档】✅ PROJECT_STATE.md / MEMORY.md / docs/xxx
【完成状态】✅ 已完成
```

---

## 9. 问题闭环规范

- 发现问题 → 全项目扫描同类问题
- 修复完成 → 更新 `PROJECT_STATE.md` 已知问题列表
- 分析根因：代码 / 流程 / 规范 / 数据
- 举一反三，预防同类隐患
- 记录经验到 `MEMORY.md`

---

## 10. 运维监控规范

- 定时任务必须可观测、有日志
- 每日数据对账、指标核对
- 异常自动告警，不依赖人工查看
- 配置变更（cron/端口/环境变量）必须记录
- 心跳巡检：邮件/日历/数据/日志

|------|-----------|

## git 提交流程

改完 + 验证通过后，由我执行 git 提交：

```bash
git add <改过的文件>
git commit -m "说明"
```

提交时将自动触发：
- **`prepare-commit-msg` hook**：显示项目阶段和规范摘要
- **`pre-commit` hook**：强制跑 `check_engineering.sh`，不通过阻止提交

紧急绕过（不推荐）：`git commit --no-verify`
