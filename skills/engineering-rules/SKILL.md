# 工程规范（StockAnalysis）v6.0

**适用场景：** StockAnalysis 项目开发。AI 开发必须按「流程 + 规范 + 检查」三步执行，禁止自由发挥。

**强制原则（无例外）：**
- 所有代码必须遵循本规范
- 禁止私自改架构、禁止无注释代码
- 数据类代码必须做单位校验 + 合理性校验
- 所有修改必须可追溯、可验证、可回滚
- 文档与代码必须同步更新

## 3. 开发全流程规范（10 步，必须逐行执行）

### 3.1 改前必做（不可跳过）

1. 读取 `PROJECT_STATE.md`，明确当前状态
2. **读本 skill**（没错，你正在读的就是），确认当前规范全部条款
3. 明确本次改动目标、影响文件、影响范围
4. 检查是否有同类代码需要同步修改
5. 确认数据单位、字段、接口规则
6. 确认关联需求/方案文档已存在

### 3.2 开发过程

1. 使用项目统一代码模板，不手写裸代码
2. 必须加注释：功能、参数、返回、异常、单位转换
3. 禁止 magic number（无注释硬编码）
4. 异常必须捕获，不能静默失败
5. 数据采集必须做：非空、范围、阈值、单位校验

### 3.4 AI 改前自检清单（强制）

**每次开始写代码前，必须口头过一遍以下清单，不可跳过：**

```
✅ [确认] 需求范围是否明确？影响哪些文件？验收标准是什么？
✅ [文档] project-doc/<项目>/requirement/ 下是否有匹配的需求文档？无 → 先生成（规范见 project-doc/文档规范.md）
✅ [文档] project-doc/<项目>/design/ 下是否有方案设计？复杂改动无 → 先生成
✅ [状态] PROJECT_STATE.md 是否已读？当前项目状态是否清晰？
✅ [规范] skills/engineering-rules/SKILL.md 是否已读？最新版本？
✅ [改后] 改完后是否会跑 tests/check_engineering.sh？
```

**规则：** 检查未通过前，禁止写任何代码。

### 3.5 改后必做（不可跳过）

1. 运行质量门禁脚本：`bash tests/check_engineering.sh`
2. 运行端到端验证，确保流程不中断
3. 数据结果校验（偏差 < 5%）
4. 更新文档：`PROJECT_STATE.md` + `MEMORY.md`
5. 问题必须闭环，扫描同类问题
6. **按固定格式输出改后总结（见第 8 条）**

## 4. 代码编写规范

### 4.1 通用规则

- 变量名/函数名：见名知意，禁止 `a`/`b`/`c` 单字符
- 一个函数只做一件事，长度不超过 80 行
- 禁止深层嵌套（不超过 3 层）
- 日志等级：INFO / WARNING / ERROR 必须明确

### 4.2 数据代码强制规范（最高优先级）

- 采集代码第一行：注明数据源单位
- 单位转换必须加注释：`# 手 → 股 ×100`
- 校验公式：`amount / volume ≈ close` 偏差必须 < 5%
- 不同板块（主板/科创/北交）单位必须统一
- API 失败必须有重试机制（3 次）

### 4.3 数据库规范

- 连接必须使用统一工具类（`dao.py`）
- 禁止裸写 SQL，防止注入
- 写入前必须校验数据格式
- 操作必须带日志

### 4.4 异常与告警规范

- 异常必须输出明确信息
- 数据异常必须触发告警，不隐藏
- 定时任务必须输出执行结果
- 禁止空 `except` 捕获

## 5. 质量门禁规范

### 5.1 必须通过检查

- 语法检查：无报错、无警告
- 工程规范：目录、命名、注释合规
- 数据校验：单位、范围、偏差合规
- 数据库检查：连接正常、核心表存在
- 模块检查：可正常导入、无循环依赖

### 5.2 检查不通过处理规则

- AI 必须自动修复，禁止提交人工
- 修复后重新检查，直到通过
- 无法修复必须记录根因，更新文档

## 6. 文档规范

- **项目文档统一存放于 `project-doc` 根路径**，权威规则见 `project-doc/文档规范.md`（路径结构 + 命名规则：`req/des/testcase/testrep/rpt-日期-描述-版本.md`）
  - 需求 → `project-doc/<项目>/requirement/`（req-），产品文档+原型
  - 设计 → `project-doc/<项目>/design/`（des-）
  - 测试 → `project-doc/<项目>/test/`（testcase-/testrep-）

- `MEMORY.md`：记录坑点、经验、最佳实践

- 禁止只写代码、不写文档
- 产出文档后**必须回读验证**：`ls` + `cat`/`head` 确认落盘，证据写入汇报

## 6.5 📄 文档交付履约契约（强制，最高优先级）

> 背景：架构/QA 等子 agent 曾出现「口头说写了方案文档，实际未落盘」的虚报事故，导致主 agent 与主人误判进度。此为流程/机制缺陷，必须根治。

### 6.5.1 刚性规则（无例外）

凡架构（design-doc）/QA（qa-subagent）/需求（requirement-doc）/研发等子 agent 的任务是「产出文档 / 交付物」，则：

**交付 = 真实落盘 + exec 验证，缺一不可。**

即：
1. **真实落盘**：用 `write` 工具把文档实际写入指定绝对路径的文件，确认文件系统上确实存在该文件；
2. **exec 验证**：执行 `ls -l <绝对路径>` + `wc -c <绝对路径> < <target-file-size>` 核对文件存在 + 字节数符合预期。

### 6.5.2 强制回复格式

交付文档的子 agent 回复中**必须**包含以下三项，缺任一项即视为「未交付」：

```
【落盘路径】<绝对路径>
【文件字节数】<wc -c 实际输出值>
【落盘验证】<exec 验证标准输出片段，如 ls -l / wc -c 的原始输出>
```

### 6.5.3 主 agent 验收 gate（强制）

委派子 agent 产出文档后，**主 agent 必须亲自 `exec` 核对文件存在 + 字节数**，核验通过后才允许向主人报「完成」。子 agent 的汇报仅作为线索，不作为验收依据。

### 6.5.4 红字警告

🚨 **禁止**只回「我写了 / 开始写了」就宣告完成——这是本次事故的根因。**未实际落盘且文件系统可见 = 未交付**，一切以 `file` 真实存在为准。

- 只口头声称、无落盘文件 → 视为未交付，需打回重做
- 落盘未 exec 验证、或字节数为 0/异常 → 视为未交付
- 向主人汇报前未做主 agent exec 复核 → 流程违规

## 11. QA 验证规范

### 11.1 提测时机
所有非 trivial 的代码改动，必须通过 QA subagent 验证后才能提交 git。

### 11.2 trivial 例外清单（不需要提 QA）
以下情况不需要提 QA，其他任何改动都必须走 QA 验证：
- 仅改注释/文档/README（不含逻辑代码）
- 仅改工程规范 SKILL.md 自身
- 仅更新非代码文件：`.gitignore`、`LICENSE`

**改了 .py 文件的一律走 QA，没有例外。**

### 11.3 QA 工作流

```
开发完成 → sessions_spawn QA subagent（task中明确要求写文件）→
  QA 执行验证 →
  QA 用 write 工具将报告写入 project-doc/StockAnalysis/test/testrep-<日期>-<描述>-v<X.X>.md →
  QA 用 message 工具发送结论到 channel →
    ✅ 通过: 主 agent 提交 git（hook自动检查最新QA报告）
    ❌ 不通过: 打回附根因 → 主 agent 修复 → 重新提测
```

### 11.3.1 主 agent spawn 规范（强制）

主 agent 每次 spawn QA subagent 时，**必须在 task 末尾加上以下内容**（不可省略）：

```
### ⚠️ 强制收尾流程
完成所有验证后，按以下顺序严格执行：
1. 先用 `write` 工具将完整测试报告写入 project-doc/StockAnalysis/test/testrep-<日期>-<描述>-v<X.X>.md
2. 再用 `message` 工具发送结论到本channel
3. 顺序不可颠倒，缺一不可
```

### 11.4 QA 结论处理
- ✅ 通过 → 开发者可以提交 git
- ❌ 不通过 → 开发者修复后重新提测
- QA 有否决权，测试不通过不能提交

### 11.5 QA 测试覆盖要求

#### 11.5.1 并发/连续请求测试（新增 2026-07-16）

❗ **Web 服务类改动，QA 必须额外覆盖：**

- **连续请求测试**：同一 API 连续调用 ≥5 次，全部返回 200，无连接错误
- **并发请求测试**：模拟 10 线程同时请求同一 API，全部返回 200，无 `InterfaceError` / `Packet sequence number wrong` 等连接异常
- **跨接口连续请求**：连续调用不同 API（market-overview → sectors → limit-up → picks）≥3 轮，全部成功
- **连接异常恢复测试**：模拟连接断开场景（如 kill MySQL 连接后恢复），后续请求能自动重建连接

> 原因：2026-07-16 生产发现 `dao.py` 单连接模式下连续请求导致连接损坏，后续全部 `Failed to fetch`，但 QA 单次请求均通过。

## git 提交流程

改完 + 验证通过后，由我执行 git 提交：

```bash
git add <改过的文件>
git commit -m "说明"
```

提交时将自动触发：

- **`pre-commit` hook**：强制跑 `check_engineering.sh`，不通过阻止提交

### 四、提交流程门禁（QA 关口，2026-08-06 定稿，必须遵守）

**提交到 git 前必须区分改动类型：**

| 改动类型 | 是否走 QA | 能否直接 commit+push |
|---------|----------|----------------------|
| 文档（方案/设计/报告/规范） | 否 | ✅ 可直接 commit+push dev |
| 代码（功能/修复） | **必须** | ❌ 必须先 QA 验收通过，才可 commit+push dev |

**代码开发的标准顺序（严禁颠倒）：**
1. RD 在开发环境（`StockAnalysis-dev`）开发
2. RD 自测
3. **QAAgent 验收（连开发库 `stock_analysis_dev`）**
4. **验收通过后** → 提交 commit
5. push 到 origin/dev
6. 生产 pull dev → 部署重启 → 生产跑通全流程 → dev→main merge

**红线：**
- 严禁先 push 到 git 再做 QA（2026-08-06 曾因 RD 自行 commit+push 未经 QA 而回退纠正）
- QA 结论（可否提交）是代码进入 dev 分支的唯一依据
- RD 不得自行 push 代码改动（只做开发+自测，提交由 QA 通过后执行）
- hard reset 会连工作区一起清空；如需回退，先 `git format-patch` 备份改动再 `git reset --hard`
